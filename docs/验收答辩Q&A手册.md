## 第二篇 三个取舍故事(前两个必背,第三个备用;90% 的分在这)

> 考官听完你的故事,一般就顺着这个方向问,所以把这两个故事讲到"让人觉得你真的想过"。每一个故事都对应考官那句"**为什么使用这个技术**"——用故事回答"为什么"。

### 故事一:点赞为什么走 Redis,不直接写 MySQL?(进阶③ 设计取舍)

**30 秒回答:**
> "点赞是**读多写多的热点数据**,而且都是同一个帖子被大量用户同时点,如果每个点赞都开一次 MySQL 事务,慢而且给数据库压力大。所以我把点赞状态先记在 Redis:一个帖子一个集合,内容是点赞人 id,点赞/取消就是集合的增删,天然**原子操作**,读状态就是查集合,Fast 且零大表压力。MySQL 里的 likes 表由**后台同步协程定时落库**,做到了最终一致;进程退出时优雅关闭,把没同步的再刷一次;另外每天对账,把 Redis 和 MySQL 的差集补上,保证数据最终一样。"

**展开讲(被追问细节):**
- 为什么不用 MySQL 事务直接写?—— 点赞是高频操作,单次事务要写一条记录 + 更新计数字段;MySQL 单机写入能力大约几千/秒,点赞热点动辄上万,QPS 扛不住;Redis 单机 10 万+,且集合操作微秒级。
- 为什么叫"最终一致"而不是"强一致"?—— 点赞这种数据,**用户视角就是"我点了立刻变成已点赞"**,Redis 这一步已经保证;MySQL 里面的记录晚几秒/几分钟来,不影响任何用户感知。用**一致性换取吞吐**,这是经典取舍。
- 崩溃了怎么办(Redis 数据丢了)?—— 对账兜底:同步协程定时比对 MySQL 与 Redis,缺失的补上,多余的删掉;即使 Redis 数据全丢,下次对账也会把它重新对齐;真实系统里点赞数丢几秒重新算出来,用户无感。
- 为什么是"集合"不是"字符串记个数"?—— 集合可以精确知道**谁**点了赞(查点赞状态接口要用的),还能去重;单纯计数回答不了"这些人是谁"。

### 故事二:Agent 为什么不引入 Eino 框架,而是手写规则?(进阶② 设计取舍)

**30 秒回答:**
> "需求原话是 Eino 方案,属**选做项**,而且我们的计划文档附录 B 里给了降级授权,允许用**规则 + AI 对话结合**实现同等能力。我评估下来:引入 Eino 学习成本高、依赖重,而**需求核心是'多轮对话 + 工具执行 + 安全发布'**,这些用**关键词规则判断意图 + 工具接口**就能落地。所以我做了手写规则 Agent:底层工具实现 `AgentTool` 接口(有 Name、Description、Call 三个方法),以后想换真 LLM(Eino),**只换最上层的意图判断层,工具和会话存储都不动**——这就是把变化隔离在一个点上,是面向接口的好处。"

**展开讲:**
- 怎么判断用户意图?—— 关键词规则:消息里含"列表/看看"→ 列表工具;含"详情/帖子"→ 详情工具;含"发/帮我发"→ 发帖草稿;**前一动作是列表时,"第 2 页"这种没有新关键词的消息,自动接着翻页**(用会话里存的 LastTool 字段)。不是 LLM,是规则,但体验上像 LLM。
- 会话为什么存 Redis?—— 一个 `session_id` 一个会话,历史是一个 JSON(对话记录 + LastTool),Redis 字符串存,设置 **30 分钟滑动 TTL**:每次对话刷新过期时间,30 分钟没聊自动清掉,防止内存被无效会话占满。
- 发帖为什么是"草稿 + 确认"两个步骤?—— **安全设计**:AI/用户说"帮我发一条某某帖",不能直接落库(万一 AI 误判或用户手滑就发错帖了)。所以第一步只生成草稿(Redis,300 秒过期),返回 `pending_action + confirm_draft_id`,告诉用户"请您确认"→ 用户回 confirm → **这时候才落库,并立刻删除草稿**;重复 confirm 会 404,因为草稿是一次性的。**防误发、防重复发**。
- 规则会不会很蠢?—— 会。但考官要看的是**你对取舍的判断**:规则 Agent 在已知有限的场景里 100% 确定性,免费的;LLM 上线要 API 费用、响应慢、有幻觉。我的取舍是:**这个作业场景里,规则比 LLM 更合适**。

### 故事三(备用):错误处理为什么做统一错误码?(进阶①)

**30 秒回答:**
> "如果我在每个 handler 里手写 HTTP 状态码,会写很多重复代码,而且容易漏。我做了统一错误码:一个 `New(httpStatus, code, msg)`,**错误自己带着状态码和业务码**;handler 只管 `return err`,全局错误中间件统一捕获、统一响应格式。这样**用户永远看到的是统一格式的提示,内部堆栈全部进日志文件**,不会暴露给用户——这正是群里考官强调的'错误信息不包含敏感信息'。"

## 第三篇 分模块 Q&A(高频问题 + 答案)

### A. 项目架构

**Q1:为什么用三层架构(handler/service/dao)?**
> 每一层只管一件事:handler 收请求、绑参数、放响应;service 写业务规则(比如"只能删自己的帖");dao 写数据库。**改业务只动 service,换数据库只动 dao**,互不干扰。当时我零基础,分层也帮我每次只关注一小块,一次只学一个概念。

**Q2:为什么选 Go + Gin + GORM?**
> Go:编译型、性能和并发好,很适合后端;语法简单,零基础两周可以上手。Gin:路由、中间件、参数绑定全都是现成的,写接口很顺。GORM:对象化操作数据库,不用手写 SQL,开发快,而且**它用占位符参数化查询,天然防 SQL 注入**(加分点,主动说出来)。

**Q3:参数校验怎么做的?**
> 结构体上打 binding 标签,handler 里 `ShouldBindJSON` 绑定;手机号 11 位、标题评论非空都是这样校验的,校验失败返回 400 提示。

### B. 数据库设计(他说"给你表结构都喷出来了"——这节一定要熟)

**4 张表背下来:**

| 表 | 关键字段 | 一句话理由 |
|---|---|---|
| users | id, username(唯一), password(bcrypt), phone(11位), role(admin/user) | 账号;role 区分管理员 |
| posts | id, author_id→users, title, content, created_at | 帖子;软删除(有 deleted_at) |
| comments | id, post_id→posts, author_id→users, content, created_at | 评论;外键保证作者和帖子真实存在 |
| likes | (user_id, post_id) **联合主键** | 一个用户对一个帖子只有一条,天然不重复 |

**Q1:likes 为什么用联合主键而不是自增 id?**
> 点赞的本质就是"谁赞了哪个帖",联合主键 `(user_id, post_id)` 正好表达这个,并且**数据库层面保证一个用户只点赞一次**,不用再写 if 查重;点赞就是 INSERT,取消就是 DELETE,切换逻辑很简单。

**Q2:为什么用外键?**
> 保证完整性:评论的作者和帖子必须在表里存在;删帖子前外键约束提醒我处理关联数据,防止残留孤儿数据。

**Q3:为什么用软删除(deleted_at),不直接 DELETE?**
> 软删除只是打个标记,数据还有,以后做"回收站"、"恢复"方便,也保留了审计痕迹。代价是查询要过滤 `deleted_at IS NULL`,我建了索引。**(加分:主动说"—般删除不要直接物理删;定期清理这种代价是定时任务"可后续做")**

**Q4:索引有哪些?为什么要?**
> comments 的 deleted_at、posts 的 created_at(时间排序)、外键关联字段都建了索引,让查询走索引,大表不慢。

### C. 鉴权与安全(毛佳俊:"鉴权改改就行"——重点)

**Q1:JWT 原理,为什么不用 Session?**
> 登录成功我签发一个 JWT(token 里放 user_id、role、过期时间),**签名加密封装**,以后每个请求带上(`Authorization: Bearer xxx`),服务端解签验证,不用查库就知道你是谁。**Session 是服务端存状态**,扩容要同步 session,JWT 是无状态,本质是把状态丢给客户端自己保管,服务器只验签名,**水平扩展天然友好**。

**Q2:中间件怎么做鉴权的?为什么要中间件?**
> `AuthMiddleware` 统一从请求头取 token、解签、把 user_id 和 role 挂到上下文,后续 handler 直接取。**中间件的好处是"横切关注点"**:所有需要登录的接口挂上这个中间件就保护了,不用在每个 handler 里写重复的 if;将来要改鉴权逻辑(如加黑名单、加过期刷新)只改一处。

**Q3:管理员权限怎么控制?**
> 角色写在 token 里(role=admin),`AdminMiddleware` 拿出来校验。删帖是通用的 handler,但注册路由时分了两条:普通用户走 `DELETE /posts/:id`(校验本人),管理员走 `DELETE /admin/posts/:id`(验完登录再验 role)。

**Q4:密码为什么不能明文存?**
> 怕数据库泄露。我用 **bcrypt 加盐哈希**,单向不可逆:登录时把用户输入的密码再哈希一次跟库里的比对,相同即通过。就算整个数据库被人拷走,他也拿不到原文。

**Q5:防 SQL 注入?**
> 用 GORM 的占位符绑定参数,参数永远不拼进 SQL 字符串,注入无从谈起。(加分:raw SQL 场景也只用 `Where("x = ?", val)` 这种写法)

**Q6:接口被恶意刷怎么办?(限流)**
> 给点赞接口加了 **Redis 限流中间件**:同一用户 2 秒内第 11 次请求就返回 429。实现是 INCR 一个计数 Key,第一次 INCR 时设置过期,计数超过 10 就拒绝;**Redis 出故障时选择放行**(可用性优先,不因为防护把自己搞挂)。

### D. 错误处理与日志(毛佳俊的原话就来自这里)

**Q1:你怎么保证 errors 信息不包含敏感信息?(必背!)**
> 三层保障:一,**错误码把"给用户看的"和"给日志看的"分开**——用户响应只有 `{code, msg}` 里的提示文字(如"用户名或密码错误"),**没有 SQL 语句、没有数据库密码、没有内部堆栈**;二,具体错误(如"duplicate entry"、堆栈)全部打进日志文件;三,全局错误中间件兜底,没被 handle 的错误也走统一格式,不会出现把 panic 堆栈吐回前端。**(直接背毛佳俊/杨翼道的原话:**"一般情况前端会把 msg 拿去给用户看,具体错误服务器自己留日志里就行了"**)**

**Q2:讲讲你的统一错误处理。**
> `errcode.New(httpStatus, code, msg)`:HTTP 状态码(400/401/403/404/429)决定响应状态,业务码(比如 10010 限流)给前端做业务判断,msg 是给用户看的。handler 写业务时不再自己猜状态码,**只管返回错误**,写起来清爽,格式也永远是统一的。

**Q3:日志系统?**
> zap 结构化日志写文件,配合 **lumberjack 按大小轮转**:单文件超过限额自动切分、保留最近 N 个,防止日志无限增长占满磁盘。开发时 console,运行时文件。

### E. 点赞与 Redis(进阶③)

**Q1:点赞的完整链路?**
> 点一下 → 中间件查 token、限流 → handler 调 service:**Redis 集合增删对应帖子的成员 + 计数** → 返回当前状态。读点赞状态走批量接口(一次 `IN` 查列表所有帖,不逐个查)。后台 `LikeSyncer` 协程定时(如每 30 秒)把 Redis 的集合和计数**批量写入 MySQL likes 表**,进程退出时再刷一次兜底,启动时顺便对账。

**Q2:数据会不会不一致?能接受吗?**
> **能,这是有意的取舍**——《最终一致》:哪怕 MySQL 里晚一分钟,用户当前看到的点赞状态永远是对的(看的是 Redis);对账兜底保证 Redis/MySQL 最终一致。强一致要每次点完立刻写两处,牺牲性能,不值得。

**Q3:Redis 挂了会怎么样?**
> 点赞属于"可降级"功能:我会在同步层做兜底,点赞失败降级(返回友好提示/或直接写库的备选,取决于实现)。面试可以诚实说:**"这个场景我先保 Redis 可用的可靠性,如果要上生产,我会加 Redis 哨兵/集群 + 降级开关"** —— 答出思路就行(杨翼道说过)。

### F. 热门排序(进阶④)

**Q1:排序规则?**
> `GET /posts?sort=hot`:**热度 = (点赞数 × 点赞权重 + 评论数 × 评论权重) × 时间衰减**。点赞权重 > 评论权重(点赞行为更便宜,或按业务定义);时间衰减让**新帖有新鲜度加成、随时间自然回落**,否则老爆款永远占榜,新帖没曝光机会。

**Q2:为什么不能直接按点赞数倒序?**
> 会变成"老的赢了":一个半年前的帖子一直第一,新写的帖子永远上不了榜。加上时间衰减,评论数和点赞数会自己"归位",**新内容给流量,内容生命周期也健康**。

**Q3:性能上怎么实现?**
> 排序是在查询阶段算的,因为帖子的点赞数/评论数就在表里,单次查询配合索引即可,没有全表扫描。(⚠️ 答题前打开你的热门排序文件,把**具体公式和权重数值**抄一遍背下来,被追问"具体多少"就说真实值)

### G. Agent(进阶②,你最该讲的亮点,10 分钟都讲不完)

**Q1:为什么做规则版不做 Eino?** —— 见「故事二」。

**Q2:多轮对话怎么做到的?**
> 两个东西:一是**会话历史持久化在 Redis**(JSON 字符串),把"上一次聊了什么"记住;二是 **LastTool 记录最近一次用的工具**,当用户只说"第 2 页"或只说一个数字时,没有关键词也能推断是接着上次的翻页/看详情动作。没有大模型也能"记住上下文",靠的是**状态,不是模型**。

**Q3:为什么要"两次确认"才发帖?**
> 发帖是写操作,让一句话就落库存风险(误发、重复)。所以先出草稿(pending_action + confirm_draft_id),用户确认后才真正写库,并且**草稿一次性、300 秒过期**,防重复、防过期。这正是"**LLM 写操作要 human-in-the-loop**"(人在回路)的朴素实现,放在互联网公司是标准安全实践。

**Q4:以后怎么升级成真 LLM?**
> 工具实现了 `AgentTool` 接口,升级只换"意图判断":把 contains 规则换成"提示词 + 工具列表"给模型,模型输出"调用哪个工具什么参数"→ 我现在的工具层直接执行,**会话持久化、草稿确认、安全闸门全部复用**。代码里已经预留好了这个口子——这就是"面向接口而非面向实现"。

### H. 测试(加分展示!)

**Q1:怎么验证功能没写错?**
> 写了**全功能回归脚本**(Python,58 项断言):注册/登录/发帖/评论/点赞/删除/权限/管理员/Agent 全流程自动化验证,一键跑,58/58 通过(其中 Agent 专项 20 项);另有业务 curl 全流程脚本当(接口走查)。**特别说明:** 脚本做成**幂等的**——每次运行随机生成全新测试用户,重复跑不污染数据也不会失败,这是我自己踩过的坑(原来固定用户名,第二次跑就失败,后来改成随机+时间戳)。

## 第六篇 现场修 bug 逃生指南(群友公认"最难",其实是送分题)

> 群友:"如果说现场出了bug能修吗""这个不可能了"——**他们都觉得修不了,你练过就能形成降维打击。**
> 记住:考官看的是**思路和淡定**,不是要你秒修。杨翼道原话:"你能说出来应该怎么弄就行"。

### 6.1 考官大概会怎么"出招"、你怎么接

| 玩法 | 具体操作 | 你怎么接 |
|---|---|---|
| 改参数 | "把热门权重改 0.1""限流放 5 次""JWT 过期改 1h" | 这**不是 bug,是现场改代码**,见 6.3 演练 1-3 |
| 打断链路 | 把 Redis/MySQL 停了看你的反应 | 服务报错别慌:说"这是没上生产时的取舍",再讲降级/哨兵/集群思路 |
| 制造脏数据 | 数据库塞个不存在作者的帖子/空标题 | 当场用 SQL 查出来删掉,展示你会 SQL(背熟 2 条:查、删有问题的行) |
| 只出不进 | 请求打了服务器没反应 | 看服务日志里的 AccessLog(请求行),判断是中间件拦了还是处理挂了 |

### 6.2 真出 bug 的五步动作(心里默数,每步 5 秒,显得在思考)

1. **"我先复现一下"** —— 再发一次请求,确认不是手滑(30% 是 curl 拼错、服务没重启)
2. **"我看看服务日志"** —— 切到服务窗口或 `logs/app.log`,看最后一堆报错,**把报错内容读出来给考官听**(读出来=你在定位,不丢人)
3. **"先看错误码"** —— 响应 msg 就是线索:401 鉴权 / 403 权限 / 404 不存在 / 429 限流 / 400 参数,对着 `errcode.New(...)` 找到那一行
4. **"我看下上下文"** —— 传参、用户 id、帖子 id 是否对(从日志看请求体)
5. **还搞不定?"三句急救法"收住**: "我先定位到 XXX,完整修法我要查一下资料,思路是 XXX"

### 6.3 4 个"现场改代码"演练(考官最容易出,练一遍就稳)

> 原理:考官要的不是你背代码,而是"**改了知道去哪改、改了知道会变什么**"。每个都练:改 → 重启(go run .)→ 重新请求 → 效果可见。

1. **改热门排序权重**:hot 排序文件里的权重改小(如 0.35 → 0.05),重启,请求 `GET /posts?sort=hot`,排序就变了 —— 考点:知道热度公式在哪个文件、公式长什么样
2. **改限流阈值**:`middleware/rate_limit.go` 的 `>10` 改成 `>3`,重启,连刷 4 次点赞,第 4 次 429 —— 考点:中间件职责 + Redis 计数 key 的过期时序
3. **改 JWT 过期时间**:签发处(或 config)的过期值改短,旧 token 立刻失效 —— 考点:无状态鉴权,过期由签名验证控制
4. **现场加一个接口(也可能让你做)**:仿照现有 GET 接口加一个"返回帖子标题长度",5 分钟改完 —— 考点:三层架构,新功能要 路由→handler→service→dao 各加一段

**考前 30 分钟**:把 1-3 在本地真实改一次再改回来,手的肌肉记忆就是答案。考官讲完你 1 分钟改好、重启、演示效果 —— 这就是全场最高光。
